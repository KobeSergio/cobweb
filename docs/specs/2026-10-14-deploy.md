# Deploy: specification

Phase 5, first sub-project of four (deploy; phases; whitelist and holder snapshot; airdrop and settings).
Product decisions: [../MASTER_PLAN.md](../MASTER_PLAN.md#decisions) (Contracts, Flow, Lock, Mint groups)
and the Phase 5 section of the same file ("factory call from the creator's wallet, address recorded from
the event, mint page address made permanent"). What the screen already shows with sample data:
[2026-10-03-creator-flow-ui.md](2026-10-03-creator-flow-ui.md) section 4.5 and the pre-reveal section 7.
The contracts: `contracts/src/CobwebFactory.sol` (`deployCollection`, `predictCollectionAddress`,
`collectionFees`, the `CollectionDeployed` event) and `contracts/src/CobwebCollection.sol` (the
constructor). The chain the fee was paid on: [2026-10-09-lock-and-pay.md](2026-10-09-lock-and-pay.md)
section 5 (`render_jobs.quote_chain_id`, "Deploy must use the same chain"). What a finished render leaves
behind: [2026-10-12-render-job-state.md](2026-10-12-render-job-state.md) section 3 (`base_uri`,
`placeholder_image_cid`, the placeholder job). The payment confirmation this mirrors:
`confirmCore` in `apps/web/src/lib/art/lock-core.ts` and `components/upload/pay-machine.ts`. Legacy
reference: [../legacy/market-creator-flow.md](../legacy/market-creator-flow.md) section 6.2 (the address
was read from `logs[0]`, the phases travelled in the constructor, unknown reverts were swallowed).

## 1. Goal

A creator with a rendered collection (or a deferred one with its placeholder pinned) deploys the contract
from the Deploy screen: the server prepares the exact constructor from the collection and the finished
render, the wallet switches to the chain the fee was paid on, simulates and sends the factory's
`deployCollection`, and the server records the contract from the factory's `CollectionDeployed` event
after verifying the receipt, which marks the collection `deployed`, freezes its chain and makes the mint
page link permanent. The deployed view shows what landed; Manage drop opens.

## 2. Decisions taken in the design conversation

1. **Phase 5 is four sub-projects**: deploy (this one); phases (mint groups on the dashboard and on
   chain); whitelist and the holder snapshot; airdrop and settings (reveal, payout, royalty, withdraw,
   mint on behalf, the transfer validator and the lock). Each is its own spec, plan and branch.
   Considered: one plan for the phase (too large to review; the deploy is the gate the other three
   depend on).
2. **The contract lives on the chain the fee was paid on.** When the collection has a done real job,
   the deploy chain is that job's `quote_chain_id`: the creator does not pick a chain, the wallet
   switches to it. A deferred collection has paid nothing yet (a placeholder lock has a zero quote and
   no chain), so the creator picks the chain at deploy, and the real art's fee is quoted on it later
   because `lockCore` reads `collections.chain_id` once it is set. Either way `collections.chain_id` is
   written at deploy and never changes. Considered: a free chain picker for every collection (the fee
   would have been paid on another chain than the contract, which the lock spec forbids).
3. **The server prepares, the wallet signs exactly that, the server proves it by address.** A read-only
   action builds the constructor arguments from the collection row, the finished render and the
   creator's form, encodes them, picks the salt and predicts the CREATE2 address. The browser simulates
   and sends the factory call with those bytes. The confirming action rebuilds the same arguments from
   the same inputs, decodes the `CollectionDeployed` log from the factory, and records the contract only
   when the event's address equals the prediction, so a contract whose init code differs from what the
   server prepared is never recorded. Nothing is stored before the receipt. Considered: a pending
   `deployments` row written at prepare (stale drafts to clean up, two writes for one fact).
4. **The collection artifact ships from the shared package.** `packages/shared` gains the entry
   `@cobweb/shared/collection`, generated from the Foundry build by the existing copy script: the creation
   code, its keccak256 hash and the collection ABI. The factory ABI gains the deploy entries. A unit test
   and a CI step assert that the shipped hash equals a fresh `forge build` of the pinned compiler
   settings, and `foundry.toml` pins `evm_version`, so the hash the admin approves on the factory is the
   hash the web app sends. Considered: fetching the artifact at request time (a build output served by
   the app; the hash drifts silently).
5. **The salt is the collection id**, its 16 uuid bytes left-aligned in 32, as the job id is for
   payments. With the factory at the same address on every chain, the predicted address is the same
   everywhere for the same creator and arguments.
6. **One deployment row per collection.** `deployments` records what was sent and what landed (the
   arguments as prepared, the fee snapshot read at prepare, the salt, the deployer, the transaction, the
   time); `collections` keeps `status`, `chain_id` and `contract_address`, which the mint page and the
   freshness server read; the launch phases become `mint_groups` rows. One service-role function
   writes all three. Considered: the deploy columns on `collections` (a wide table wider).
7. **Name, symbol and description freeze at lock**, the item owed since Phase 3: the metadata the
   worker writes and the contract's name must agree. The frozen-field guard refuses the change once
   `art_locked_at` is set, and the Details screen shows the three fields read-only from then on.
8. **Deploy opens for a deferred collection once its placeholder job is done**, with the collection
   still `draft`; `stageContext` learns whether a done placeholder job exists. Today only sample mode
   reaches Deploy with deferred art.
9. **Fees and the cost are read in the browser** through wagmi on the deploy chain
   (`collectionFees()` on the factory; the gas of the simulated call times the gas price), as the pay
   step reads `jobPayment`. The server reads the fees again at confirm for the snapshot.
10. **The deployed view's primary action is Manage drop.** The public mint page is Phase 6 and answers
    404 in real mode today, so "Open mint page" waits; the link is shown as text with the note that the
    page opens with Phase 6. Considered: a disabled button (a control that never works is noise).
11. **Recovery as in the pay step**: the sent hash and the form values are remembered in localStorage
    under `cobweb-deploy:<collectionId>` until the server records the contract, and "I have a
    transaction hash" confirms a transaction sent from elsewhere.

## 3. Scope

In: the deployments migration (the table, the two guard changes, `collection_record_deploy`, the
placeholder readiness for the stage rules); the shared package's collection artifact and the factory
ABI entries with their hash check; the two server actions and their cores; the deploy machine, the
screen on real data, the deployed view; sample mode on the same screen; `verify:deploy`; docs.

Out: everything after deploy (phases, whitelist, airdrop, settings, reveal: the next three
sub-projects); the public mint page (Phase 6); contract verification on an explorer (Phase 7); a
testnet or mainnet factory (Phase 7); a per-wallet cap on collections (Phase 7).

## 4. Database (`supabase/migrations/20261014100000_deploy.sql`)

### 4.1 `deployments`

```sql
create table public.deployments (
  collection_id uuid primary key references public.collections (id) on delete cascade,
  chain_id integer not null check (chain_id > 0),
  factory text not null check (factory ~ '^0x[0-9a-f]{40}$'),
  deployer text not null check (deployer ~ '^0x[0-9a-f]{40}$'),
  salt text not null check (salt ~ '^0x[0-9a-f]{64}$'),
  code_hash text not null check (code_hash ~ '^0x[0-9a-f]{64}$'),
  args jsonb not null,
  contract_address text not null check (contract_address ~ '^0x[0-9a-f]{40}$'),
  tx_hash text not null unique check (tx_hash ~ '^0x[0-9a-f]{64}$'),
  base_uri text not null,
  payout_address text not null check (payout_address ~ '^0x[0-9a-f]{40}$'),
  royalty_bps integer not null check (royalty_bps between 0 and 1000),
  royalty_receiver text not null check (royalty_receiver ~ '^0x[0-9a-f]{40}$'),
  public_max_per_wallet integer not null check (public_max_per_wallet >= 1),
  mint_fee_flat_wei numeric(78, 0) not null check (mint_fee_flat_wei >= 0),
  mint_fee_bps integer not null check (mint_fee_bps between 0 and 10000),
  airdrop_fee_per_token_wei numeric(78, 0) not null check (airdrop_fee_per_token_wei >= 0),
  deployed_at timestamptz not null default now(),
  created_at timestamptz not null default now()
);
```

`args` is the constructor as prepared (section 6.1), kept so the arguments can be re-encoded and the
address re-derived later. Row-level security: the owner reads (`private.collection_owned`); no client
role writes (grants: select to `authenticated`; everything else through the function below).

### 4.2 `collection_record_deploy`

```sql
create function public.collection_record_deploy(
  p_collection_id uuid, p_owner uuid, p_chain_id integer, p_factory text, p_deployer text,
  p_salt text, p_code_hash text, p_args jsonb, p_contract_address text, p_tx_hash text,
  p_base_uri text, p_payout_address text, p_royalty_bps integer, p_royalty_receiver text,
  p_public_max_per_wallet integer, p_mint_fee_flat_wei numeric, p_mint_fee_bps integer,
  p_airdrop_fee_per_token_wei numeric, p_groups jsonb
) returns public.deployments
language plpgsql security definer set search_path = ''
```

Service role only (revoked from `public`, `anon`, `authenticated`, as `art_lock`). Locks the
collection through `private.lock_owned_collection(p_collection_id, p_owner)`. Refusals, all `23514`:

1. `status = 'deployed'` or a `deployments` row exists: 'The contract is already deployed.'
2. `slug is null`, or `slug_reserved_at < now() - interval '3 days'`: 'Reserve your mint page link
   first.'
3. `max_supply is null`: 'Set the supply in Art first.'
4. The collection has no done job to start on: no real job in state `done`, and (for a deferred
   collection) no placeholder job in state `done`: 'Render the art before deploying.'
5. `p_tx_hash` already recorded on another deployment: 'This transaction was recorded for another
   collection.' (`23505` from the unique index is mapped to the same sentence in the web app).

Then, in one transaction: insert the `deployments` row; update `collections` with `status =
'deployed'`, `chain_id = p_chain_id`, `contract_address = p_contract_address`, and `slug_reserved_at =
null` (the link is permanent; `private.reserve_slug` already treats a deployed collection so); insert one
`mint_groups` row per element of `p_groups` (`onchain_id` the element's index, `name`, `price_wei`,
`max_supply`, `start_at` null), deleting any `mint_groups` rows the collection had before (a draft set
from an earlier Phases visit is replaced by what the constructor took). The frozen-field guard's
lapsed-slug branch cannot fire (refusal 2 ran first).

### 4.3 The guard: name, symbol and description freeze at lock

In `collections_guard_frozen_fields`: when `old.art_locked_at is not null` and `new.name`, `new.symbol`
or `new.description` differs from the old value, raise 'The name, symbol and description cannot change
while the art is locked.' (`23514`). The existing `deployed` branch stays (a deployed collection is also
locked, so the new branch fires first with its own sentence; the old sentence is kept for a deployed
collection whose `art_locked_at` is null, which does not happen in practice). `frozenDetailFields`
(section 9) mirrors it.

### 4.4 The stage rule's input

`private.placeholder_ready(p_collection_id uuid) returns boolean`: true when the collection has a
placeholder job in state `done`. Exposed to the owner as `public.collection_placeholder_ready(uuid)`
(authenticated, the owner check of the read policies). The deploy page and `stageContext` ask it for a
deferred collection (section 9).

## 5. The shared package

### 5.1 The collection artifact (`packages/shared/src/collection.ts`, entry `@cobweb/shared/collection`)

Generated by `packages/shared/scripts/copy-abi.ts` from `contracts/out/CobwebCollection.sol/CobwebCollection.json`
and the factory artifact, in the same run that writes `factory-abi.ts`:

```ts
export const COLLECTION_CREATION_CODE: Hex   // the artifact's bytecode.object
export const COLLECTION_CODE_HASH: Hex       // keccak256(COLLECTION_CREATION_CODE)
export const collectionAbi                   // the whole ABI, as const
```

Its own entry, because the creation code is about 41 KB of text and only the deploy screen and the
confirming core need it; `@cobweb/shared` (the index) does not re-export it.

### 5.2 The factory ABI

`copy-abi.ts` adds `deployCollection`, `predictCollectionAddress`, `collectionFees`, `isCollection`
and the `CollectionDeployed` event to `WANTED`, so `factoryAbi` carries them. `packages/shared/src/factory-abi.test.ts`
asserts the entries exist.

### 5.3 The hash check

`packages/shared/src/collection.test.ts`: `COLLECTION_CODE_HASH` equals `keccak256(COLLECTION_CREATION_CODE)`;
the creation code is under 24,576 bytes; and, when `contracts/out/CobwebCollection.sol/CobwebCollection.json`
exists, its bytecode equals the shipped one (the test skips with a message when the artifact is absent).
CI's contracts job runs `forge build` then `pnpm --filter @cobweb/shared test`, so a compiler drift fails
the build. `contracts/foundry.toml` pins `evm_version` to the value the pinned solc defaults to today,
and `DeployLocal.s.sol` and `Deploy.s.sol` keep approving `keccak256(type(CobwebCollection).creationCode)`,
which is the same bytes.

### 5.4 Address prediction (`packages/shared/src/deploy-address.ts`, in the index)

```ts
export function collectionSalt(collectionId: string): Hex           // 16 uuid bytes, left-aligned
export function encodeCollectionArgs(args: CollectionArgs): Hex     // abi.encode of the constructor
export function predictCollectionAddress(input: { factory: Address; deployer: Address; salt: Hex; creationCode: Hex; args: Hex }): Address
```

`CollectionArgs = { name: string; symbol: string; payout: Address; baseUri: string; maxSupply: bigint; groupSupplies: bigint[]; groupPrices: bigint[]; publicMaxPerWallet: bigint; royaltyBps: number; owner: Address; royaltyReceiver: Address }`.
`predictCollectionAddress` is viem's CREATE2 formula with `keccak256(abi.encode(deployer, salt))` as the
factory does. `verify:deploy` compares it with the factory's view on Anvil.

## 6. The server

### 6.1 The deployment input and the prepare core (`apps/web/src/lib/deploy/deploy-core.ts`)

```ts
export type DeployForm = {
  chainId: number                                                   // the picked chain; must equal the real job's quote chain when there is one
  payout: Address; royaltyBps: number; royaltyReceiver: Address; publicMaxPerWallet: number
  groups: { name: string; priceWei: string; maxSupply: number }[]   // index 0 the public sale, 1 to 10 groups
}
export type Prepared = {
  chainId: number; factory: Address; deployer: Address; salt: Hex; codeHash: Hex
  args: CollectionArgs; encodedArgs: Hex; predicted: Address; baseUri: string; revealsTo: string | null
  fees: { mintFeeFlatWei: string; mintFeeBps: number; airdropFeePerTokenWei: string }
}
export async function prepareCore(ctx: DeployContext, form: DeployForm): Promise<DeployOutcome<Prepared>>
```

`DeployContext` is `LockContext` without the queue (the same `ownedCollection` read, the session's
wallet). The core: refuses when `status = 'deployed'` ('The contract is already deployed.'), when the
link is not live, when `max_supply` is null, and when no job to start on exists (the sentences of 4.2,
decided here first so the creator sees them before the wallet opens); validates the form with zod
(`isAddress` and not the zero address for the payout and the receiver; royalty 0 to 1000 bps; cap 1 to
`max_supply`; 1 to 10 groups, names 1 to 40 characters, unique; prices whole wei; allocations summing to
at most `max_supply`; the first group named by the creator, "Public" by default); reads the start job:
the latest done placeholder job when the collection is deferred or the real job has "Reveal later"
(`placeholder_upload_id` set), else the latest done real job; `baseUri` is that job's `base_uri` and
`revealsTo` the real job's `base_uri` when it differs; `chainId` is the done real job's `quote_chain_id`
when there is one (the form's chain must equal it, else 'The contract goes on the chain the fee was paid
on.'), otherwise the form's chain, which must be one of the available chains (`chainById`);
`factory` is `factoryAddress(chainId)` (refused as `CHAIN_NOT_READY` when unset); `deployer` is the
session wallet; `owner` is the deployer; reads `collectionFees()` on the factory through
`publicClientFor(chainId)` (refused 'The factory could not be read.' on failure). Pure helpers
(`deployArgs(collection, job, form, wallet)`, `validateDeployForm`) live in
`apps/web/src/lib/deploy/deploy-args.ts` and are unit tested.

### 6.2 The confirm core

```ts
export async function confirmDeployCore(ctx: DeployContext, txHash: Hex, form: DeployForm): Promise<DeployOutcome<DeployRecord>>
```

Mirrors `confirmCore`: `prepareCore` again (the same refusals); the hash lowercased; a hash already in
`deployments` is 'This transaction was recorded for another collection.'; `publicClientFor(chainId)`,
`getTransactionReceipt` (`NOT_CONFIRMED` when not found), a reverted receipt is 'The deployment
reverted on chain.'; the chain's confirmation depth as the payment; `matchCollectionDeployed(receipt,
{ factory, deployer, salt, codeHash, predicted })` (`apps/web/src/lib/chain/collection-deployed.ts`,
unit tested like `matchArtPaid`) decodes the factory's `CollectionDeployed` logs and answers `{ ok,
collection }` or `NOT_THIS_DEPLOY` (no log from the factory for this deployer and salt),
`OTHER_CODE` (the code hash differs), `OTHER_CONTRACT` (the address differs from the prediction, so the
arguments on chain are not the ones prepared); then `ctx.service().rpc('collection_record_deploy', ...)`
with the decoded address and the prepared values; returns the record (section 6.3). A second confirm with
the same hash answers the existing record unchanged (idempotent, as the payment).

### 6.3 The actions (`apps/web/src/app/actions/deploy.ts`)

```ts
export async function prepareDeploy(collectionId: string, form: DeployForm): Promise<ActionResult<Prepared>>
export async function confirmDeploy(collectionId: string, txHash: string, form: DeployForm): Promise<ActionResult<DeployRecord>>
export async function getDeployment(collectionId: string): Promise<ActionResult<DeployRecord | null>>
```

Through a `deployWrite` helper shaped like `lockWrite` (session, ownership, the error map;
`revalidatePath` of the collection layout after a record). `DeployRecord = { chainId, contractAddress,
txHash, deployer, deployedAt, baseUri, payout, royaltyBps, royaltyReceiver, publicMaxPerWallet, fees,
groups }`, read from `deployments` and `mint_groups` under the creator's client.

## 7. The screen

### 7.1 The deploy machine (`apps/web/src/components/deploy/deploy-machine.ts`, pure, tested)

Shaped like `pay-machine.ts`: `DeployDeps { prepare(form); switchChain(chainId); simulate(prepared): Promise<() => Promise<Hex>>; wait(hash); confirm(hash, form); remember(hash, form); forget(); sleep; now }`,
`runDeploy(input, deps, dispatch)` through the phases `preparing`, `switching` (when the wallet's chain
differs), `simulating`, `wallet`, `confirming`, `verifying`, `success`; `classifyError` reused from the
pay machine (moved to `components/deploy/tx-errors.ts` so both import it); `verifyDeploy` polls `confirm`
every 3 seconds for 2 minutes with the same terminal answers; the localStorage key
`cobweb-deploy:<collectionId>` holds `{ hash, form }`.

### 7.2 The flow (`deploy-flow.tsx`) on real data

- The page passes the collection, the start job and the real job (as `RenderJob`), the chain (from the
  start job's `quote_chain_id`), the fee snapshot read on the server (`prepareCore` without a form is
  not possible, so the page reads `collectionFees` itself through `publicClientFor`; null when
  unreadable, and the screen reads again in the browser), `readOnly`, the deployment record when
  deployed, `sample`.
- The chain picker stays for a deferred collection (the six launch chains from `availableChains`, the
  connected one marked, as today); a collection with a paid real job shows its one chain as a card with
  "Connected" or "Switch to <chain>". Either way the switch is the first step of the deploy action
  (`switchChain` from wagmi).
- The summary's predicted address comes from `prepareDeploy` (the server's prediction, so the two sides
  agree) and refreshes when the form changes (debounced 400 ms, the same action); the deploy cost is
  `estimateContractGas` of the prepared call times `getGasPrice`, "about X <symbol>", or "could not be
  estimated" when the wallet is on another chain.
- The deploy action: `prepareDeploy` (the final values), `switchChain` if needed, `simulateContract`
  on the factory with `deployCollection(COLLECTION_CREATION_CODE, prepared.encodedArgs, prepared.salt)`
  from the session wallet, `writeContract(request)`, `waitForTransactionReceipt`, `confirmDeploy`; the
  deployed view renders from the record the server answers, never from the prediction. `router.refresh()`
  after a record so the stepper and Manage drop open.
- The deployed view: the record's chain, address and transaction with explorer links, deployed time,
  mint page link as text with the Phase 6 note, payout, royalty, mint fee, the launch phases, and the
  primary action "Set up your drop" to Manage drop.

### 7.3 The form

As today (`deploy-form.tsx`, `deploy-phases.tsx`): name and symbol read-only, the supply, the link
field (required, live reservation), payout, royalty, receiver, public cap, phases at launch. The
chain picker becomes the one-chain card. The "Set the supply in Art first" hint stays for a deferred
collection without a supply.

## 8. Sample mode

The deploy page in sample mode keeps its states (`?state=deployed`, the five `?outcome=` values,
`?art=deferred`) on a `sampleDeployActions` object with the same `DeployDeps` surface: `prepare`
answers the sample prediction (the FNV address as today) and the sample fees, `switchChain`, `simulate`
and `wait` run the scripted phases with the outcome, `confirm` answers a sample record. `deploy-sim.ts`
shrinks to that object and `useCreatorWallet`; `useFactoryRead` and `predictAddress` go.

## 9. Stage rules

- `stageAccess(status, 'deploy', { artDeferred, placeholderReady })` is open when `upload` is done
  (as today) or when `artDeferred && placeholderReady`; `stageContext` reads `placeholderReady`
  through `collection_placeholder_ready` for a deferred collection (one cheap call), `false` otherwise.
- `frozenDetailFields(collection)` takes the row: `name`, `symbol` and `description` freeze once
  `art_locked_at` is set (and stay frozen when deployed); the Details screen's notice says "The name,
  symbol and description are fixed while the art is locked."
- After deploy the collection is `deployed`: Manage drop opens (as today), Deploy is read-only and shows
  the deployed view, Art stays open for deferred art.

- Unit: `deploy-args.test.ts` (the arguments from a collection, a job and a form; every validation
  sentence; the start job choice: deferred, reveal later, plain), `deploy-address.test.ts` (the salt
  from a uuid; the prediction against a vector taken from `forge test`'s
  `test_deploy_addressMatchesPrediction`), `collection-deployed.test.ts` (the event decoded from a

- `verify:local`: the guard refuses a name, symbol or description change while locked and allows it
  on a draft; `collection_record_deploy` refusals (already deployed, no link, lapsed link, no supply,
  nothing rendered, a reused hash), the record (status, chain, address, the mint groups, the link
  permanent), the deployments read policy (B cannot read A's), `collection_placeholder_ready`.
- `verify:deploy` (new, `apps/web/scripts/verify-deploy.ts`, against local Supabase and Anvil): a
  rendered collection seeded through the service role (a done real job with a base URI; a second,
  deferred collection with a done placeholder job); `prepareCore` answers the chain, the prediction and
  the fees; the script wallet sends `deployCollection` with the prepared bytes; the factory's view and
  the event agree with the prediction; `confirmDeployCore` records the contract, the groups and the link;
  the collection reads `deployed`; the contract's `name`, `symbol`, `maxSupply`, `baseURI`, `owner`,
  `royaltyInfo` and `collectionState()` match the arguments; refusals: a hash of an unrelated
  transaction (`NOT_THIS_DEPLOY`), a deploy sent with other arguments (`OTHER_CONTRACT`), a second
  confirm with the same hash (idempotent), a deploy for a draft collection (nothing rendered), the
  deferred collection deploying on its placeholder base URI. Cleanup deletes what it made.
- Foundry: unchanged tests; the `evm_version` pin keeps the bytecode; the CI contracts job adds the
  shared hash test after `forge build`.
- `pnpm typecheck && pnpm lint && pnpm test`, `pnpm build`, every verify script.
- A browser walk with the dev wallet against local Supabase, local storage and Anvil: a rendered
  collection reaches Deploy, the link is reserved, the summary shows the predicted address and the
  cost, the deploy switches nothing (the wallet is on Anvil), simulates, signs and confirms, the
  deployed view shows the address from the event (equal to the prediction), the explorer links, the
  phases, and Manage drop opens; a reload lands on the deployed view; the Details fields are read-only;
  sample mode's states still render.

## 12. Owed and known

- The public mint page (Phase 6) is where "Open mint page" returns.
- Contract verification on the explorer (Phase 7).
- The deployer pays the full creation code in calldata (about 4.5M gas); a cheaper path (a clone of an
  implementation) was ruled out by the identical-bytecode decision in Phase 1.
- A creator who deploys the prepared bytes from outside the flow with other arguments ends with a
  contract the app never records; support.
- The fee snapshot in `deployments` is informational; the contract's `fees()` is the truth.

## 13. Acceptance criteria

- [ ] `prepareDeploy` answers the chain, the prediction and the fees; the browser deploys through the
