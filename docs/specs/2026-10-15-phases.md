## 1. Goal

A creator with a deployed collection runs its phases from Manage drop, Phases, on the contract's state: the
server reads `collectionState()` and joins each group with what Cobweb keeps in `mint_groups` (name,
description, visibility, order); status comes only from the contract's `active`. Each change on chain is
simulated and sent from the creator's wallet by one manage machine and confirmed by the server from the
receipt, which re-reads the chain; names, visibility and order need no transaction. The Overview shows the
real minted total and live phases.

## 2. Decisions taken in the design conversation

1. **Scope.** Phases on real data for a deployed collection, and the Overview's minted total and live phases.
   `mint_groups` gains `description` (at most 500 characters), `visible` (default true) and `position` (the
   order, unique per collection); `price_wei`, `max_supply` and `start_at` stay a copy the server refreshes
   from the chain, never from browser values. The server reads `collectionState()` through
   `publicClientFor(chainId)` on the collection's address, cached per request, on each Manage page load and
   after every receipt through a server action, so liveness is the contract's `active` at the read's
   `blockTimestamp` (rule 1). The freshness server (Phase 6) may replace that read; nothing else changes.
   Considered: waiting for Phase 6 (rule 3 binds the mint page, not the dashboard).
2. **The chain is the source of truth** for price, allocation, minted, schedule and the flag; `mint_groups`
   keeps name, description, visibility and order, which never go on chain. The view joins them by
   `onchain_id`; a group on chain without a row (deployed outside the flow) shows as "Group N" and the
   creator can name it. Considered: the browser writing the on-chain fields, as legacy did (the copy drifts).
3. **One manage machine** (`components/manage/manage-machine.ts`, pure, the deploy machine without prepare
   and, except for Add phase, without a pending store) drives every on-chain change in Manage drop, here and in
   the next two sub-projects: `simulate` with `simulateContract` on the collection ABI from the session
   wallet, the returned send closure (rule 2), `wait`, then `confirm(hash)`, a server action that verifies the
   receipt (to the collection's address, from the owner's wallet, successful, carrying the expected event),
   re-reads the chain, refreshes the row copies and answers the fresh view. The browser never writes on-chain
   fields. Considered: wagmi hooks in each dialog (nine copies of one sequence).
4. **Add phase** takes the next free id from `mintGroups()` (the highest plus one; 0 is the public sale) and
   sends `registerMintGroup(id, price, maxSupply, startTimestamp)`; the name, description and visibility
   travel in the confirm call, written only after the receipt proves `MintGroupRegistered(id)`. A pending add
   is kept in localStorage under `cobweb-phase:<collectionId>` as `{ hash, form }` with "Check again" and
   "Discard", as the deploy's recovery, so a lost receipt never loses the name. Considered: the row written
   before the transaction (a rejected add leaves a row behind).
5. **Off-chain edits** (name, description, visibility, order) are server actions on `mint_groups` under the
   owner's row-level security with the existing checks: a name of 1 to 40 characters, unique in the
   collection ignoring case; a description of at most 500; the order as a swap of positions. The public group
   (0) can be renamed but not hidden. Considered: names on chain (no field for them; gas for every rename).
6. **The on-chain actions map one to one:** Open now `setMintGroupStatus(id, true)`; Close
   `setMintGroupStatus(id, false)` (the contract clears the schedule); Schedule `scheduleMintGroupStart(id,
   unix)` through `zonedToUnix` in the creator's time zone, UTC and the Unix value shown, `scheduleWarning`
   when already past on chain; Clear schedule `scheduleMintGroupStart(id, 0)`; Edit price
   `changeSalePrice(priceWei, id)`; Edit max supply `setMintGroupMaxSupply(id, n)`, the minted floor and the
   supply ceiling checked in the browser before the simulation; Edit per-wallet limit
   `setPublicMaxMintPerWallet(n)`, whose copy `deployments.public_max_per_wallet` the confirm refreshes; Close
   all `stopOrStartAllMintGroups(false)`. No delete: the contract has none; hide instead. Considered: one
   `setPhase` call, as legacy's plan proposed (no such function; MASTER_PLAN wins).
7. **Errors.** `classifyError` gains a `manage` subject that decodes the collection's custom errors from a
   simulation revert (`BelowMinted`, `AllocationsExceedMaxSupply`, `MintGroupAlreadyExists`,
   `MintGroupDoesNotExist`, `AddressZero`, `Unauthorized`) into sentences; anything else keeps the generic
   wording. Considered: only the browser's mirrors of the checks (they drift from the contract).
8. **The Overview on real data:** the header's chain and contract from the deployment record, "Minted N of
   M" and the live phases from the chain read; holders, proceeds and the activity list stay sample behind
   their seams until the freshness server and the settings sub-project. Considered: all sample until Phase 6.
9. **Sample mode** keeps every state Phases and the Overview show today through a `sampleManageActions`
   object with the machine's surface; `simulate.ts` and `use-transaction.ts` shrink into it, as
   `deploy-sim.ts` did. Considered: the simulated sequence beside the real one (two paths, one dialog).
10. **`verify:phases`** against local Supabase and Anvil: a collection deployed through the factory, every
    change sent from the script wallet and confirmed, the confirm's refusals and the read's failure path.
    Considered: more checks in `verify:deploy` (one script per sub-project, as before).
11. **Docs:** MASTER_PLAN's Phase 5 status line, a dated Mint groups decision for the chain-read dashboard, a
    dated note at creator-flow-ui section 4.6, and the deploy spec's parked item (the deployed view's phases
    read from `mint_groups`) closed now that the deployed view reads `deployments.args`. Considered: a
    Decisions heading for Manage drop (Mint groups already holds the rules).

## 4. Database (`supabase/migrations/20261015000000_phases.sql`)

### 4.1 `mint_groups`

```sql
alter table public.mint_groups
  add column description text not null default '' check (char_length(description) <= 500),
  add column visible boolean not null default true,
  add column position integer check (position >= 0),
  add constraint mint_groups_public_shown check (onchain_id <> 0 or visible);
alter table public.mint_groups drop constraint mint_groups_name_check;
alter table public.mint_groups add constraint mint_groups_name_check
  check (char_length(name) between 1 and 40 and name = btrim(name));
create unique index mint_groups_name_key on public.mint_groups (collection_id, lower(name));
create unique index mint_groups_position_key on public.mint_groups (collection_id, position)
  where position is not null;
revoke insert, update, delete on public.mint_groups from authenticated;
grant update (name, description, visible, position) on public.mint_groups to authenticated;
```

Existing rows take `position = onchain_id` (their names came through the deploy form, so the check and index
hold). A before-insert trigger gives a row without a position the next one in its collection, so
`collection_record_deploy` is unchanged and its rows read 0, 1, 2; both writers lock the collection first, and
`position` is null only inside a move. The owner's client reads its rows and changes only the off-chain
columns (the policy "mint_groups: owner all" stays); rows come only from `collection_record_deploy` and
`mint_group_record`, the copies only from `mint_groups_refresh`. The table comment says which is which.

### 4.2 `deployments`

```sql
alter table public.deployments drop constraint deployments_public_max_per_wallet_check;
alter table public.deployments
  add constraint deployments_public_max_per_wallet_check check (public_max_per_wallet >= 0),
  add column state_block bigint check (state_block >= 0),
  add column state_read_at timestamptz;
```

`public_max_per_wallet` becomes the copy of the contract's `publicMaxMintPerWallet()` (the value at deploy
stays in `args.publicMaxPerWallet`); 0 is allowed because the contract allows it. `state_block` and
`state_read_at` are the block, and its time, of the read the copies were last refreshed from.

### 4.3 Functions

```sql
create function public.mint_group_record(p_collection_id uuid, p_owner uuid, p_onchain_id integer,
  p_name text, p_description text, p_visible boolean) returns public.mint_groups
create function public.mint_groups_refresh(p_collection_id uuid, p_owner uuid, p_block bigint,
  p_block_time timestamptz, p_public_max_per_wallet integer, p_groups jsonb) returns boolean
create function public.mint_group_move(p_collection_id uuid, p_onchain_id integer, p_up boolean) returns void
```

All are `plpgsql` with `set search_path = ''`. `mint_group_record` and `mint_groups_refresh` are security
definers for the service role only (revoked from `public`, `anon` and `authenticated`), lock the collection
through `private.lock_owned_collection` and refuse one without a `deployments` row with 'The contract is not
deployed yet.' (`23514`). `mint_group_record` inserts the row for `(collection_id, onchain_id)` or updates an
existing one's name, description and visibility, keeping its position (a row a reorg left behind is taken
over); the checks and the name index raise as they are. `mint_groups_refresh` writes nothing and returns false
when `p_block` is below `deployments.state_block`, so a slower read never overwrites a newer one; otherwise,
for each `{ onchain_id, price_wei, max_supply, start }` of `p_groups` (`start` in Unix seconds, 0 stored as
null), it updates the row whose copies differ, sets the cap, `state_block` and `state_read_at`, and returns
true; it never inserts or deletes rows. `mint_group_move` is a security invoker for `authenticated`, under the
owner's policy and column grant: it swaps the row's position with the next lower one (up) or higher one (down)
in three updates (the row parks at null, the neighbour takes its position, the row the neighbour's), leaves an
end row as it is, and raises 'phase not found' (`42501`) for a row it cannot see.

## 6. The server

### 6.1 The chain read (`apps/web/src/lib/manage/phases-core.ts`)

```ts
/** `collectionState()` as the screens read it: counts as numbers, prices as decimal strings. */
export type ChainState = { block: bigint; blockTimestamp: number; maxSupply: number; totalMinted: number;
  publicMaxMintPerWallet: number; mintOnBehalfActive: boolean; groups: { id: number; priceWei: string;
  maxSupply: number; minted: number; startTimestamp: number; flag: boolean; active: boolean }[] }
/** At the latest block, or at `atLeast` when the node is behind it; null when the chain, its RPC or the contract does not answer. */
export type StateReader = (chainId: number, address: Address, atLeast?: bigint) => Promise<ChainState | null>
export const readCollectionState: StateReader
```

Two calls through `publicClientFor(chainId)`: `getBlockNumber({ cacheTime: 0 })`, then `readContract` of
`collectionState` at the later of that block and `atLeast` (the confirm passes the receipt's block, so a node
behind the wallet's never answers the state before the change). A failure is logged and answers null, as
`readCollectionFees`. No `server-only` marker, as `deploy-core.ts`, so `verify:phases` imports the module; the
pages read through React's `cache`, once per request.

### 6.2 The view

```ts
export type PhasesContext = DeployContext
export type PhasesView = { chainId: number; contract: Address; groups: MintGroup[]; publicMaxPerWallet: number;
  totalMinted: number; maxSupply: number; blockTimestamp: number; readAt: number; chainReachable: boolean }
export async function phasesViewCore(ctx: PhasesContext, read: StateReader = readCollectionState): Promise<DeployOutcome<PhasesView>>
```

`groups` are the chain's groups joined with their rows by `onchain_id`, in the creator's order;
`blockTimestamp` is the chain's time at the read; `readAt` is the block's time, or the copy's `state_read_at`
when the chain did not answer; `chainReachable` false means the groups are the copy and minted and live status
are unknown. The core reads the `deployments` row and the `mint_groups` rows (numeric columns as text) under
the creator's client, refusing 'The contract is not deployed yet.' without a deployment; reads the chain;
joins; and refreshes the copies through `ctx.service().rpc('mint_groups_refresh', ...)` with the read's block.
A refresh that fails, or a value too large for its column (an id or a limit above 2,147,483,647 set outside
Cobweb), is logged and never fails the view. A null read answers the copy: minted 0, flag and live false
(never shown), the collection's `max_supply`, `blockTimestamp` equal to `readAt` (the deploy time before any
refresh). Both are pure (`joinPhases`, `copyView` in `apps/web/src/lib/manage/phases-view.ts`): rows by
`position`, then `onchain_id`; a chain group takes its row's name, description and visibility, or "Group N",
"" and true with `named: false` (a new optional `MintGroup` field); unnamed groups follow by id; a row the
chain does not list is left out; `kind` is `public` for 0, else `whitelist`.

### 6.3 The confirm

```ts
export type PhaseAdd = { onchainId: number; name: string; description: string; visible: boolean }
export type PhaseTxExpected = { event: ExpectedEvent; add?: PhaseAdd }
export async function confirmPhaseTxCore(ctx: PhasesContext, txHash: Hex, expected: PhaseTxExpected, read: StateReader = readCollectionState): Promise<DeployOutcome<PhasesView>>
```

As `confirmDeployCore`, without the depth: the deployment; `publicClientFor(chainId)` (`CHAIN_NOT_READY` when
it throws); `getTransactionReceipt` (not found is `PHASE_NOT_CONFIRMED`, which the machine polls); a reverted
receipt is `PHASE_REVERTED`; `matchPhaseEvent(receipt, { contract, from: ctx.wallet, event })`
(`lib/chain/phase-events.ts`, like `matchCollectionDeployed`) refuses `NOT_THIS_CONTRACT` (`to` is not the
collection), `NOT_FROM_WALLET` (`from` is not the session wallet) or `NOT_THIS_CHANGE` (no log from the
collection decodes to the expected event and arguments); for an add, `mint_group_record` writes the row now
and only now; then the read at the receipt's block or later, the refresh and the view (the copy with the flag
when the read fails). The expected events, from the collection:
`MintGroupRegistered(id)` for `registerMintGroup`, `MintGroupStatusChanged(id, status)` for
`setMintGroupStatus`, `AllMintGroupsStatusChanged(status, any count)` for `stopOrStartAllMintGroups`,
`MintGroupStartTimestampChanged(id, start)` for `scheduleMintGroupStart`, `SalePriceChanged(id, price)` for
`changeSalePrice(price, id)`, `MintGroupMaxSupplyUpdated(id, n)` for `setMintGroupMaxSupply` and
`PublicMaxMintPerWalletChanged(n)` for `setPublicMaxMintPerWallet`. No depth is needed: everything the confirm
writes is read from the chain again on the next load, except the add's row, keyed by an id the receipt
proves. A second confirm of the same hash answers the view again.

### 6.4 The off-chain edits and the actions (`apps/web/src/app/actions/phases.ts`)

```ts
export async function getPhases(collectionId: string): Promise<ActionResult<PhasesView>>
export async function confirmPhaseTx(collectionId: string, txHash: string, sent: SentCall): Promise<ActionResult<PhasesView>>
export async function recordPhase(collectionId: string, txHash: string, add: PhaseAdd): Promise<ActionResult<PhasesView>>
export async function renamePhase(collectionId: string, onchainId: number, details: { name: string; description: string }): Promise<ActionResult>
export async function setPhaseVisibility(collectionId: string, onchainId: number, visible: boolean): Promise<ActionResult>
export async function movePhase(collectionId: string, onchainId: number, direction: 'up' | 'down'): Promise<ActionResult>
```

The last three have cores in `phases-core.ts` (`renamePhaseCore`, `setPhaseVisibilityCore`, `movePhaseCore`).
Rename updates name and description under the creator's client or, for a group without a row that the chain
lists, records one through `mint_group_record` (else `PHASE_NOT_ON_CHAIN`). Visibility refuses 0
(`PUBLIC_SHOWN`); visibility and move refuse a group without a row (`NAME_FIRST`); move calls `mint_group_move`
with the creator's client, and past either end changes nothing. Every action runs through `phasesWrite`
(`lib/manage/phases-write.ts`, `server-only`, shaped like `deployWrite`) after zod: the hash as Deploy's;
`sentCallShape` (ids 0 to 2,147,483,647, uint256 values as decimal strings), whose event is
`expectedEvent(callOf(sent))`; `phaseAddShape` (id 1 to 2,147,483,647, the name trimmed with `phaseNameError`'s
sentences, the description at most 500), whose event is `MintGroupRegistered(onchainId)`. `phasesWriteError`
maps `42501` to `NOT_FOUND`, `23505` on `mint_groups_name_key` to `PHASE_NAME_TAKEN`, `23514` on
`mint_groups_public_shown` to `PUBLIC_SHOWN`, a known Phases sentence as it is, else `UNSAVED`.

## 7. The screens

### 7.1 The calls (`apps/web/src/lib/manage/phase-calls.ts`, pure, for the browser and the server)


### 7.2 The manage machine (`apps/web/src/components/manage/manage-machine.ts`, pure, tested)

```ts
export type ManageInput = { call: ManageCall; account: string | undefined; wallet: Address; chainId: number;
  connectedChainId: number | undefined; sentHash?: Hex }   // sentHash: a remembered add, checked, never sent again
export type ManageDeps<T> = {
  switchChain(chainId: number): Promise<void>
  /** Simulates the call on the collection; resolves with the function that sends the simulated request, unchanged. */
  simulate(call: ManageCall): Promise<() => Promise<Hex>>
  wait(hash: Hex): Promise<'success' | 'reverted'>; confirm(hash: Hex): Promise<ActionResult<T>>
  remember?(hash: Hex): void; forget?(): void; sleep(ms: number): Promise<void>; now(): number
}
export async function runManage<T>(input: ManageInput, deps: ManageDeps<T>, dispatch: (event: DeployEvent) => void): Promise<T | null>
```

`runManage` reports through the deploy machine's events and reducer, without `preparing`. No account is
"Connect your wallet" ("Connect your wallet to make this change. Nothing was sent."); an account other than
the session wallet is "Use your sign-in wallet" ("Cobweb checks changes sent from <wallet>, your sign-in
wallet. Switch to that account in your wallet, then try again."); then `switching` when the wallet is on
another chain, `simulating`, `wallet`, `remember` (Add phase only), `confirming` with `wait` (a throw keeps the
hash as `unconfirmed`; a revert forgets it: "The change failed on chain", "The transaction was included but
reverted, so nothing changed. You paid gas only. Try again."), and `verifying`, which polls `confirm` every 3
seconds for 2 minutes while it answers `PHASE_NOT_CONFIRMED`, then `success`. `isTerminalManageAnswer` names
the refusals that end an attempt and forget a remembered add (`PHASE_REVERTED`, `NOT_THIS_CONTRACT`,
`NOT_FROM_WALLET`, `NOT_THIS_CHANGE`, and `PHASE_NAME_TAKEN`, which reads "The phase is on the contract as
Group <id>, but its name is taken. Name it from its menu."); any other keeps the hash for "Check again". The
steps show in the deploy's `TxProgress` ("Checking the change", "Reading the contract", the deploy's other
labels), so the manage `TxStep`, `TxPhase` and `TxProgress` go; the pending add uses the deploy's `KeyStore`.

`classifyError(error, at, 'manage')` words the wallet steps for a change ("Cancelled in your wallet", "Not
enough funds for gas", "The change would fail", "The wallet did not send the change", "The change could not
be confirmed") and, at `simulating`, the `errorName` of viem's `ContractFunctionRevertedError` among the
causes; the owner check on every Phases call is OpenZeppelin's `OwnableUnauthorizedAccount`, decoded with
`Unauthorized`. Each sentence ends "Nothing was sent."; the payment and deploy wording is unchanged.

```
BelowMinted(minted)                 It cannot go below <minted>, the tokens this phase has already minted.
AllocationsExceedMaxSupply()        The phases' allocations together would be more than the collection's supply. Lower another phase first.
MintGroupAlreadyExists(id)          Phase <id> is already on the contract. Read the contract again, then add the phase.
MintGroupDoesNotExist(id)           Phase <id> is not on the contract. Read the contract again.
AddressZero()                       The address cannot be the zero address.
Unauthorized(caller), OwnableUnauthorizedAccount(caller)
                                    Only the contract's owner can make this change, and <caller> is not the owner.
anything else                       The check against the contract failed: <short message>
```

### 7.3 The browser's actions and the dialog


### 7.4 The Phases screen

- The page calls `getPhases` and passes the view, the session wallet and `sample`; a refusal shows its
  sentence with "Try again". `PhasesScreen` takes `{ collection, view, wallet, sample }` and keeps the view in
  state (the chain is `chainView(view.chainId)`; `PhaseContext` gains `server`); the unused `deployment` prop

- Under the heading, "Read from the chain <relative to readAt>" with "Read again". When `chainReachable` is

## 8. Sample mode

`simulate.ts` becomes `components/manage/manage-sim.ts`; `use-transaction.ts` goes. `sampleManageActions` and
`samplePhasesServer` share one sample `PhasesView`: `simulate` waits 650 ms and fails as the contract would on
it (`sampleRevert(call, view)`, the mirror the dialogs' `check` functions held, thrown as a decoded revert);
`answer` settles the wallet step (Approve, Reject, Approve then revert); `wait` takes 1.6 seconds;
`nextGroupId` is one more than the highest sample id; `confirm` and `record` apply the call, recompute
`active` with `chainReadGroup` (sample only, on the sample's clock) and answer the new view; the edits take
900 ms. `SAMPLE` and `saveOffChain` move with it. `samplePhasesView(collection)` builds today's scaled sample,
so every dialog and the simulated wallet's answers render as today; new states are `?chain=unreachable` (the
copy with the alert) and `?pending=add` (the recovery panel). The Overview keeps today's sample.

## 12. Owed and known

- The freshness server (Phase 6) replaces the server read and brings live state; until then the screens change
  only on a read, so a start that passes while the page is open reads "Scheduled" until the next one.
- The Whitelist tab (the next sub-project), Airdrop and Settings still run on sample data, their dialogs on the
  sample actions; a whitelist needs its group's row, so an unnamed group is named first.
- A replaced transaction (sped up or cancelled) is never matched: the confirm checks the hash the wallet
  returned; the next read shows the chain, and a replaced add's entry is discarded before naming "Group N".
- Per-group `MintGroupInfo` has no name: the freshness server and the mint page (Phase 6) join `mint_groups`
  for names, descriptions, visibility and order; `components/mint/model.ts` still sorts by status.
- The copy is only as fresh as the last read that reached the chain; a row whose group a reorg removed stays
  until its id is registered again. An id or a limit set outside Cobweb above 2,147,483,647 does not fit the
  copy: that group cannot be named, and the refresh skips that read.
