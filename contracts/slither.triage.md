# Slither triage

Every finding of Slither's run that has an element under `contracts/src`, with its verdict and reason
(docs/specs/2026-10-18-load-run-contract-review-and-cloudflare.md, section 7.2). `slither.config.json` keeps such a finding whatever library code it cites as evidence, and leaves out a finding whose elements all lie in the libraries. The `accepted` and `false positive` findings are in `slither.db.json`, the triage database Slither's `--triage-mode` wrote, which every later run reads to hide them, so CI's `slither` job fails only on a medium or high finding nobody has judged. A finding that cites a statement or a pragma carries its file and line numbers in its id, so any edit that moves those lines reopens it, a line added above them included: triage it again in the change that moved it. No `slither-disable` comment goes into `src/`, since solc's metadata hash would move the creation code hash the factories approve.

- Analyzer: slither-analyzer 0.11.6 on Python 3.12 through uv, crytic-compile building through Foundry with the solc 0.8.30, prague and 200 optimizer runs that `foundry.toml` pins.
- Command, from `contracts/`: `uvx --python 3.12 --from slither-analyzer==0.11.6 slither . --config-file slither.config.json`, with `--triage-mode` to write the database. CI's `slither` job runs the same analyzer from the repository root as `slither contracts --fail-medium --config-file=contracts/slither.config.json --triage-database contracts/slither.db.json`, which gives every finding the same id.
- Run: 19 October 2026, at commit `82ed358`, on the contracts as they stand since `94a6c1f`, creation code hash `0xa57eac3d6d8dca5d3bb294162c964342bd351cba3cf034f1b8b6b3e2ca9ae594`.
